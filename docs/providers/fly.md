# Fly Machines adapter

The Fly adapter is the first bundled compute provider. It uses the Machines API
directly and can scale to zero idle workers.

Install and authenticate the Fly CLI before continuing. The GitHub repository
or organization and the two Fly app names should match the values generated by
`runneryard init`.

## Isolation layout

Create two apps on two custom private networks. The controller only needs the
Machines API and does not need private network access to workers.

```sh
fly apps create acme-ci-runners --network runneryard-workers
fly apps create acme-ci-controller --network runneryard-control
fly volumes create runneryard_state \
  --app acme-ci-controller \
  --region cdg \
  --size 1 \
  --yes
```

Initialize the empty ledger exactly once, before starting the controller. The
command refuses to overwrite an existing ledger:

```sh
fly machine run ghcr.io/gwendall/runneryard:0.1.1 \
  --entrypoint "/usr/local/bin/controller-entrypoint" \
  --env RUNNER_BUDGET_FILE=/var/lib/runneryard/budget.json \
  --app acme-ci-controller \
  --region cdg \
  --volume runneryard_state:/var/lib/runneryard \
  --rm \
  -- budget init --file /var/lib/runneryard/budget.json
```

Controller startup never creates a missing ledger. If the volume or file is
lost, it fails closed until an operator investigates; do not run `budget init`
as an automatic restart hook.

The worker app must remain secret-free:

```sh
fly secrets list --app acme-ci-runners
```

## Worker credential

Create a deploy token scoped to the worker app:

```sh
fly tokens create deploy --app acme-ci-runners
```

Store it as `FLY_API_TOKEN` only on the controller app. Never set it on the
worker app.

## GitHub App

Create and install a GitHub App only on the repositories that will use this
fleet. Repository-scoped scale sets need Metadata read and Administration
read/write. The app does not need a webhook. Generate one private key and keep
its client ID, installation ID, and private key only in the controller's secret
scope.

## Deploy

Use the generated `.runneryard/fly.controller.toml`. The same public image
contains the controller binary and worker runtime; the adapter replaces the
entrypoint for workers and passes only their JIT configuration.

```sh
fly secrets set --app acme-ci-controller \
  FLY_API_TOKEN='<worker-app token>' \
  GITHUB_APP_CLIENT_ID='<client id>' \
  GITHUB_APP_INSTALLATION_ID='<installation id>' \
  GITHUB_APP_PRIVATE_KEY='<private key PEM>'

fly deploy \
  --app acme-ci-controller \
  --config .runneryard/fly.controller.toml \
  --image ghcr.io/gwendall/runneryard:0.1.1 \
  --ha=false
```

Pin a version in production. `latest` is suitable only for a disposable canary.

## Machine defaults

The adapter creates one Machine with:

- `auto_destroy=true`
- restart policy `no`
- a 30-second SIGTERM window
- 4 shared CPUs, 8 GB RAM, and 30 GB ephemeral rootfs by default
- controller, lease, runner, and deadline metadata
- `ACTIONS_RUNNER_INPUT_JITCONFIG` as its only injected credential
- process-level `ignore_app_secrets=true`, plus a non-secret lease deadline

Configure shape and cost through `RUNNER_CPUS`, `RUNNER_MEMORY_MB`,
`RUNNER_ROOTFS_GB`, `MIN_RUNNERS`, `MAX_RUNNERS`, and
`RUNNER_MAX_LIFETIME`, `RUNNER_USAGE_BUDGET`, and `RUNNER_BUDGET_WINDOW`.
The generated controller mounts `runneryard_state` at `/var/lib/runneryard`
for a fail-closed durable usage ledger.

## Rollback

Stop the controller before deleting either app. Confirm
`fly machines list --app acme-ci-runners` is empty, revoke the worker-app token,
then delete the two apps. Route workflows back to `ubuntu-latest` first so jobs
do not remain queued on the removed scale set.
